# 驗證狀態

把設計依賴的技術主張分成三類：已在模擬器實測、官方文件記載但沒實測、還只是設計。

## 1. 01A 探針怎麼跑的

- 環境：這個雲端工作環境（Node 22、Java 21），`firebase-tools` 13.35.1、`@firebase/rules-unit-testing` 4、`firebase` 11，Firestore 模擬器。
- 探針是**拋棄式**的簡化規則＋測試腳本，放在工作階段的暫存資料夾，**沒有進 repo**，也沒有連任何真的 Firebase 專案。目的只是確認平台能力，不是正式規則；正式規則與完整測試是 01B 的工作。
- 結果：24 項全部通過（2026-11-11，連跑兩次結果相同）。
- 這次環境連不到 `firebase.google.com` 與 `docs.cloud.google.com`，標〔文件〕的數字來自搜尋引擎回傳的官方頁摘要。02 前請你在官方頁或主控台再看一次額度與價格。

## 3. 官方文件記載、還沒實測〔文件〕

| 主張 | 用在哪裡 |
|---|---|
| 一次提交（批次、交易）是原子的；正式環境同一份文件的寫入依序生效 | 防重複預約、一次性核銷在正式環境的保證 |
| 規則讀取上限：單一文件請求與查詢 10 次；批次與交易整批 20 次，每個操作仍是 10 次；可能被快取的讀取不計次 | 讀取預算 |
| 規則不是篩選器，查詢條件要讓規則能判斷 | 查詢設計 |
| 一批最多 500 筆寫入；單一文件最大 1 MiB | 匯入分批 |
| Spark 免費額度：每天 5 萬讀、2 萬寫、2 萬刪；1 GiB 儲存；每月 10 GiB 流出；太平洋時間午夜重置；每次查詢至少 1 次讀取 | 額度估算 |
| 主控台與 Admin SDK 不經過規則 | 信任邊界 |
| custom claims 需要 Admin SDK（伺服器或 Functions） | 不用 custom claims 的理由 |
| 受管匯出（排程備份）需要啟用計費 | 手動匯出 |
| 網頁 SDK 可以用 ES module 從 CDN 載入，不需要打包器 | 01B 的載入方式 |
| 交易在離線時失敗；批次在離線時排隊 | 預約用交易 |
| 瀏覽器不會把網址 `#` 之後的部分送到伺服器 | QR 權杖放在 `#join=` |
| GitHub push ruleset 不提供給免費方案的公開 repo | 權杖方案不採用 ruleset |
