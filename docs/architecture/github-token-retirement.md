# GitHub 權杖的最早安全撤銷方案

修正階段 00 風險 1：階段 00 把「作廢權杖」放在全部切換之後、而且說它不可逆。這兩點都要修正。

## 1. 先確認的事實（已從程式碼確認）

| 事實 | 依據 |
|---|---|
| **讀取不需要權杖。** 開頁時從 GitHub Pages 直接讀資料檔；之後的輪詢 `cloudPull` 只有「有權杖才帶」，沒有權杖就用未登入的 GitHub API（每小時 60 次） | `core/js/boot.js` 的 `dataReady`、`core/js/cloud.js` 第 22～27 行 |
| 權杖只用在寫入（`cloudPush` 的 PUT） | `core/js/cloud.js` 第 43～56 行 |
| 權杖用密碼加密後放在每個部門的公開資料檔（`sync.tokenAll`、`sync.tokenEnc`、`members[].tok`） | `auth.js`、`provision.js`、`save.js` |
| 權杖能寫整個 repo，包含網站程式 | 階段 00 第 2.2 節 R1 |

推論：

- **作廢權杖的後果只有「大家暫時不能存檔」**，網站照常顯示、資料不會遺失。還沒存出去的修改留在各自裝置的 localStorage（可以用匯出備份救回）。
- **作廢不是不可逆**：作廢的是「那一把」權杖。真的需要回到 GitHub 寫入模式，可以再產生一把新的。所以沒有理由把作廢拖到 03～09 全部做完。

## 2. 三段式方案

### 第一段：現在就做（不用等 Firebase，不改程式，你在 GitHub 上操作）

| # | 動作 | 效果 |
|---|---|---|
| T1 | 到 GitHub → Settings → Developer settings → Personal access tokens 檢查這把權杖：必須是 **fine-grained**、只授權 `LinkMasterKing/-` 這一個 repo、權限只有 **Contents：Read and write**（加上自動附帶的 Metadata：Read）。**不能有** Workflows、Administration、Secrets、Pages、Actions 等權限。如果是 classic token，立刻換成 fine-grained | 確認權杖不能改 GitHub Actions、repo 設定、祕密 |
| T2 | 重新產生一把權杖，**到期日設成「預計最後一個部門切換日＋14 天」**（建議先設 2027-01-31，見決策 D10），用看板現有的後台流程換上新權杖並重新輸入全會密碼，舊的那把作廢 | 到期日是保險：就算計畫延誤或忘記，權杖也會自己失效；要延長必須有人主動決定再發一把 |
| T3 | 同一次換權杖時，**換掉全會密碼**（如果它曾經發給現任幹部以外的人、或貼在群組裡） | 外流的舊密碼解不開新權杖 |
| T4 | 開啟 repo 的 Watch → All Activity 通知；每週看一次「不是透過 PR 進 main、又改到程式」的 commit（指令見第 4 節） | 萬一有人用權杖改程式，一週內發現 |
| T5 | 把第 3 節的緊急程序存給會長室 | 懷疑外流時不用討論就能先作廢 |

T2、T3 會經過看板自己的「網站管理」流程寫入資料檔，那是你平常的操作；我不會碰權杖，也不會改資料檔。

評估過但**不建議**的做法：

| 做法 | 為什麼不建議 |
|---|---|
| GitHub push ruleset 限制只能改 `data*.json` | push ruleset 不提供給免費方案的公開 repo〔搜尋到的官方說明：push ruleset 只用於 private／internal repo；未在 GitHub 設定頁實測〕。而且權杖代表的是你本人（repo 管理員），管理員本來就能略過規則 |
| 分支保護「main 一定要經過 PR」 | 看板直接寫 main，會讓所有部門無法存檔 |
| 改用另一個只有寫入權限的機器帳號持有權杖 | 要多管一個 GitHub 帳號；而且上一項不能用，機器帳號仍然能改程式。只延後問題 |
| 把資料檔搬到另一個只放資料的 repo，權杖只授權那個 repo | 真的能讓權杖改不到程式，但要搬資料檔（違反 `CLAUDE.md` 第 1 條，需要你特別同意）、改 `cloud.js` 與 `dept/config.js`，工作量約一個 PR。**只有在 02 延誤超過一個月時才值得做**（決策 D10） |

### 第二段：02 驗收後，逐部門切換（[migration.md](migration.md) 第 5 節）

- 切換的部門改走 Firestore，不再用權杖寫入。
- 建議節奏：水果部 → 一個資料少的部門 → 其餘六個空白或幾乎空白的部門一次切 → 活動部、社務部 → 權益部。資料量很小（全會合計 50 張卡片），**目標是在 02 驗收後 14 天內全部切完**，不等 03。

### 第三段：作廢（最早的安全時間點）

**條件全部成立就作廢，不等 03～09：**

| # | 條件 |
|---|---|
| C1 | 10 個部門都已切到 Firestore，而且至少連續 3 個工作天沒有任何部門切回 GitHub |
| C2 | 至少做過一次 Firestore「匯出全部資料」，並在模擬器上還原成功 |
| C3 | 會長室編輯量、編輯紀錄已改讀新來源（`cards/*/versions`、`auditLogs`），不再依賴 commit |
| C4 | 回復方案已改成「從 Firestore 匯出還原」；確認作廢後還需要 GitHub 寫入時，是「再發一把新權杖」而不是沿用舊的 |

作廢由你在 GitHub 上親自操作。作廢後：

1. 開一個清理 PR：移除 `provision.js`、`cloud.js` 的寫入路徑、設定頁的權杖與全會密碼畫面。
2. 資料檔裡的加密權杖已經沒有作用。要不要另外把資料檔清成不含 `sync`、密碼雜湊的版本，是你親自確認的一次資料檔修改（階段 00 的 8-13）。
3. 通知現有 11 個身分：看板密碼如果跟別的服務相同，請去改那個服務的密碼（雜湊還在 Git 歷史裡，改寫歷史不實際）。

**時程比較**

| | 階段 00 計畫 | 本方案 |
|---|---|---|
| 降低風險 | 無 | 現在（T1～T5） |
| 權杖自動失效的期限 | 無 | T2 設定的到期日 |
| 作廢 | 03～09 全部做完、穩定之後 | 最後一個部門切換後 3 個工作天，目標是 02 驗收後約 3 週內 |

## 3. 緊急程序（任何時候都可以執行）

懷疑權杖或全會密碼外流時：

1. **立刻作廢權杖**（GitHub → Settings → Developer settings → 該權杖 → Revoke）。網站繼續可讀，所有人暫時不能存檔。
2. 用第 4 節的指令檢查最近有沒有不是透過 PR 進來的程式修改；有的話在 GitHub 上 revert。
3. 決定要不要再發一把新權杖（加上 T2 的到期日、T3 換全會密碼），還是直接加速切換到 Firestore。

## 4. 每週檢查指令

列出最近 14 天改到程式（不是資料檔）、而且不是 PR 合併的 commit：

```bash
git fetch --deepen=500 origin main && git log origin/main --since="14 days ago" --no-merges --format="%h %an %ad %s" --date=short -- . ':(exclude)data.json' ':(exclude)data-*.json' ':(exclude)archive'
```

`--deepen` 是給淺層複本（shallow clone）用的：淺層複本最舊的那筆 commit 會被誤判成「新增了所有檔案」。01A 寫這份文件時實際跑過一次（2026-11-11，最近 14 天）：補齊歷史後沒有任何存檔格式的 commit 改到程式。

正常情況下輸出只會有 PR 裡的 commit（訊息是功能說明，不是「〔名字〕類別｜內容」的存檔格式）。看到存檔格式的訊息卻改到程式，就要警覺。
