## 0. 結論（先看這裡）

1. **現有架構撐不住這次改版的核心需求。** 現在是「整份 JSON 檔＋一把共用的 GitHub 權杖」：沒有可信任的身分、沒有部門層級的寫入限制、所有資料公開、沒有交易。Google 登入授權、QR 一次性核銷、預約互斥、私人時段、點名個資，都必須有後端規則把關，純前端做不到。
2. **建議方案：Firebase Authentication＋Cloud Firestore＋Security Rules，先用免費方案（Spark），Cloud Functions 列為備案。** 這次列出的需求（角色審核、QR 原子核銷、預約互斥、版本不可改）都能用「交易＋安全規則」做到，不必一開始就升級到要綁信用卡的方案。網站仍然是 GitHub Pages 靜態前端，不加打包器。
3. **目前正式站有一個要優先處理的安全問題**（第 2 節）：公開的資料檔裡放著「用全會密碼加密的 GitHub 權杖」，而那把權杖能改整個 repo（包含網站程式）。等於知道全會密碼的人都能改網站。切換到新後端後要作廢這把權杖。
4. **建議的安全順序**：00 核准 → 01A 設計 → 01B 在模擬器實作與遷移演練 → 02 登入與權限 → **正式切換（先水果部、再逐部門）** → 03 → 04 → 05 → 06；07、08／08B 在 02 之後可另開分支；09 最後。規格沒有寫明「哪一步切換正式資料」，建議放在 02 驗收後、03 開始前，獨立成一個關卡（第 7 節）。
5. **有 14 項要你決定或提供**（第 8 節），其中 4 項會擋住 01A：付費方案、資料公開分級、誰是第一位總管理員、舊身分怎麼對應 Google 帳號。

## 2. 現行授權方式與安全風險（已確認）

### 2.1 現在怎麼運作

- **讀**：任何人不用登入就能讀所有部門的資料檔（GitHub Pages 公開提供）。
- **寫**：瀏覽器拿一把 GitHub fine-grained 權杖，用 Contents API 把整份 JSON 寫回 `main`。用檔案的 sha 擋同時修改（後存的人收到 409／422）。
- **權杖怎麼到每個人手上**：權杖用密碼加密（AES-GCM，金鑰由 PBKDF2-SHA256 210000 次導出）後存進公開的資料檔：`sync.tokenAll`（全會密碼）、`sync.tokenEnc`（部門共用密碼）、`members[].tok`（個人密碼）。輸入對的密碼，瀏覽器解出權杖、存進 localStorage。
- **身分**：`members[]` 的名字是自己填的；個人密碼的雜湊（`members[].kdf`）也在公開檔案裡。「管理員／成員」「後台管理員（`?admin`）」「秘書處會議編輯要會長室開放」都只是介面上的判斷。
- **紀錄**：每次存檔是一筆 commit，訊息寫「〔名字〕類別｜內容」。50 筆近期 commit 的 Git 作者全是同一個 GitHub 帳號（權杖的主人），名字只寫在訊息裡。

### 2.2 風險

| # | 風險 | 嚴重度 | 說明 |
|---|---|---|---|
| R1 | 一把權杖能寫整個 repo，包含網站程式 | 高 | 權杖權限是「這個 repo 的 Contents 讀寫」。解得開的人不只能改任何部門的資料，還能改 `index.html`、`core/js/*`，等於能對所有使用者植入程式。 |
| R2 | 加密過的權杖放在公開檔案 | 高 | 每個部門檔都有 `sync.tokenAll`。知道全會密碼（發給所有部門）就能解開；不知道的人也能離線無限次嘗試。密碼夠長時暴力破解不實際，但全會密碼是多人共用、會外流的那一種。 |
| R3 | 沒有部門隔離 | 高 | 任何拿到權杖的人都能寫所有部門。介面上的部門身分擋不住直接呼叫 API。 |
| R4 | 身分無法驗證 | 中 | 名字自填、commit 訊息由前端組出來，可以冒名。編輯紀錄不能當稽核依據。 |
| R5 | 個人密碼雜湊公開 | 中 | `members[].kdf`、`pwKdf` 在公開檔案與 Git 歷史裡，可離線嘗試。若有人把常用密碼拿來當看板密碼，風險會外溢到別的服務。 |
| R6 | 所有內容公開 | 依內容 | 即時回報說明、專員名字、會議紀錄修改內容、會長室文件連結（`docs[]`）任何人都讀得到。目前沒有私人資料類別；06（會長私人時段）、07（點名）絕對不能沿用這種存法。 |
| R7 | 整份檔案為單位的衝突 | 中 | 兩個人同時改同一部門的不同卡片，後存的人整份被擋。03 的原位編輯、逐行勾選會讓這個問題變成日常。 |
| R8 | 讀取靠輪詢 | 低 | 每 60 秒或回到分頁才拉一次；未帶權杖的 GitHub API 每小時 60 次限制。不是真的即時。 |
| R9 | 授權不可撤銷 | 中 | 權杖一旦存進某台裝置的 localStorage，除非整把作廢，否則收不回來。作廢又會讓所有人失效（交接說明八十三「還沒做」那一項）。 |

| 類別 | 項目 |

| **保留**（畫面與行為不變，只換資料來源） | 所有版面與動畫（`anim.js`、`motion.js`、`pagefx.js`、`splash.js`、`nav.js` 工具列）、甘特圖與議題、燈號規則、會議要報告、每週概述、工作報告、搜尋、通知層既有外觀、PWA 安裝、深淺色、匯出備份 |

## 3. 現有架構能不能支援後續功能

| 後續功能 | 現有架構 | 原因 |
|---|---|---|
| Google 登入＋部門授權（02） | 不行 | 沒有可信任的一方能驗證「這個 Google 帳號可以寫這個部門」。純前端判斷可被繞過（CHANGE_SCOPE 共通限制 5 明確禁止）。 |
| QR 一次性邀請（02） | 不行 | 一次性、到期、併發核銷都需要後端原子操作。 |
| Keep 式原位編輯、逐行勾選（03） | 勉強、不建議 | 資料結構可以用 schemaVersion 14 加進 JSON，但整檔衝突（R7）會讓「點外面自動儲存」經常失敗。 |
| 版本歷史不可改（04） | 不行 | 有權杖的人可以改寫任何內容；「帳號 UID」也不存在。 |
| 全會活動／會議共享事件（04、05） | 部分 | 現在全會行事曆是讀全部部門檔再合併，沒有統一事件 ID；能顯示，但做不到「活動部才能標全會活動」。 |
| 會長私人時段、預約互斥（06） | 不行 | 私人資料不能放公開檔案；互斥要交易。 |
| 點名與名冊（07） | 不行 | 個人出缺席資料不能公開；快速連點會撞整檔衝突。 |
| 首頁 Switch 風格、手機卡片堆（08、08B） | 可以 | 純前端。但卡頓的根因跟「整頁重新載入」有關（見 7.3 的 08）。 |
| 開場動畫分鏡（09） | 可以 | 純前端，現有 `splash.js` 已經是拆字、只動 transform／opacity 的做法。 |

結論：02～07 需要新資料層；08、08B、09 與資料層無關，但規格要求排在權限穩定之後（首頁要顯示登入狀態）。

## 4. 後端方案比較與建議

### 4.1 Firebase 在 GitHub Pages 靜態前端下適不適合

適合，理由：

- 前端直接用官方 SDK 連 Firestore，授權由 **Security Rules 在伺服器端**判斷，不是前端判斷。符合「不能用純前端當授權伺服器」。
- SDK 可以用 ES module 直接從官方 CDN 載入，或把檔案放進 repo（例如 `core/vendor/firebase/`），**不需要 npm 打包**。現有 script 是一般 script，可以用一支 `type="module"` 的橋接檔把資料層掛到全域給現有程式用（推論：01A 要做一個最小驗證）。
- Firestore 有即時監聽與離線快取，可以取代 60 秒輪詢與自製的離線唯讀。
- 交易與批次寫入是原子的，Rules 可以用 `getAfter()`／`existsAfter()` 檢查同一批寫入的其他文件，足以做 QR 核銷與預約互斥。

要注意的限制（推論，02 要實機驗證）：

- **Google 會擋 LINE、Instagram、Facebook 內建瀏覽器的登入**。從 LINE 點連結進來的人要先「用瀏覽器開啟」才能登入。所以「不登入也看得到公開內容」很重要（見 5.2 分級）。
- 登入視窗在「安裝成 App」的全螢幕模式（尤其 iPhone 加入主畫面）行為不一。備案是改用 Google Identity Services 的按鈕取得憑證，再交給 Firebase。
- 網站網域是 `linkmasterking.github.io`，要加進 Firebase Auth 的授權網域。

### 4.2 方案比較

| 方案 | 優點 | 缺點 | 評估 |
|---|---|---|---|
| **A. Firebase Auth＋Firestore＋Rules（免費方案）** | 不用寫伺服器；規則在伺服器端強制；即時、離線、交易都有；免費方案不用綁信用卡、超量只會當天停用不會收費；Google 登入原生支援 | 規則語言要學、要寫規則測試；免費方案沒有 Cloud Functions、沒有自動排程備份；有每日讀寫額度 | **建議** |
| B. A＋Cloud Functions | 可做寄信通知、排程清理、較複雜的後端檢查、自訂權杖欄位（custom claims） | 需要升級成用量計費方案並綁付款方式；多一層要維護的程式 | 備案：遇到規則做不到的需求再加，逐項提出 |
| C. Supabase（Postgres＋RLS） | SQL 與資料列權限表達力強；也有 Google 登入與即時 | 免費專案一段時間沒人用會被暫停（推論：寒暑假風險，需查現行政策）；資料模型與現有 JSON 差更遠 | 不建議 |
| D. Cloudflare Workers＋D1 | 完全掌控 | 登入驗證、權限、即時、離線都要自己寫；交接給下一屆的維護成本最高 | 不建議 |
| E. Google Apps Script＋試算表 | 學生會熟悉試算表 | 併發與交易弱、速度慢、有執行配額；做不到預約互斥的保證 | 不建議 |
| F. 維持 GitHub，改用 GitHub 登入 | 改動最少 | 每個人都要有 GitHub 帳號；權杖交換仍需要伺服器；解決不了 R1、R3 | 不建議 |

### 4.3 免費方案夠不夠（推論，數字以官方現行文件為準，01A 查證）

- Firestore 免費額度大約是每天 5 萬次讀取、2 萬次寫入、1GB 儲存。
- 目前全會合計 50 筆即時回報。開一次部門看板估 30～100 次讀取（進行中的卡片＋議題＋設定）；完成紀錄改成切到那一頁才讀。以每天 300 次開啟估算約 3 萬次以內。
- 風險：公開可讀代表任何人都能消耗讀取額度。緩解：App Check、完成紀錄分頁載入、首頁不讀各部門明細。超量的後果是當天停止服務，不會產生費用。

### 4.4 環境

- 兩個 Firebase 專案：開發用（例 `stustsa-board-dev`）與正式用（例 `stustsa-board`），再加本機的 Emulator Suite 跑自動測試。01B 只碰模擬器。
- 開發工具（`firebase-tools`、規則測試套件）只放在 `backend/` 之類的資料夾，不進網站載入路徑。盤點時確認這個雲端環境有 Node 22 與 Java 21，可以跑模擬器（未驗證：模擬器程式本體能不能下載，取決於環境的網路設定）。
- Firebase 的網頁設定（apiKey、projectId 等）**不是機密**，本來就會出現在前端，可以提交；真正不能進 Git 的是服務帳戶金鑰、OAuth 用戶端密鑰。計畫是完全不產生服務帳戶金鑰（見 6.3）。

### 5.3 卡片與逐行混合內容

```
cards/{cardId}
  deptId        部門代號
  title         名稱（舊 name）
  blocks        陣列，順序即顯示順序：
    { id        穩定的行 ID（建立時產生，之後不變）
      text      這一行的文字（可以是空字串）
      check     null＝沒有核取方塊；{ done, doneAt, doneBy }＝有核取方塊與狀態
      timeId    null 或 events 集合的文件 ID（這一行的時間標記） }
  timeIds       不屬於任何一行的卡片層級時間標記（舊資料都在這裡）
  issueId       母議題
  staff         負責人（UID；遷移期間可以是 legacy:舊身分ID）
  labels、links、report（會議要報告）
  state         open｜done｜deleted；doneAt、deletedAt、deletedBy
  order         排序值
  round、roundAt、touched、touchedAt、fromEv   燈號與舊分段紀錄沿用
  version       整數，每次成功提交加一
  createdAt、createdBy、updatedAt、updatedBy
  legacyDesc    遷移時保留的原始說明全文（驗證與回復用）
```

設計理由：

- **每一行是一個物件，核取方塊是這一行的選填屬性**，不是整張卡片的模式，也不是在文字前面插符號。加上或拿掉核取方塊只動 `check`，`text` 不變，所以文字不會消失。
- 行放在卡片文件的陣列裡（不是子集合）：一張卡片的行數有限，整張卡片是一份原子快照，版本歷史直接複製這個陣列即可。
- 行 ID 穩定，拆行、合併、重排、刪除都以 ID 為準；時間標記掛在 `timeId` 上，重排不會掉。
- 併發：寫入一律用交易，帶 `version` 當前提；勾選這類單行操作在交易裡「讀最新 → 只改那一行 → 寫回」，不會蓋掉別人同時改的其他行。
- 時間只存在 `events` 集合一份。卡片的行、卡片層級標記、行事曆、全會活動都是引用同一個 ID；版本快照另外複製當時的時間值，歷史才看得到當時的內容。

舊資料怎麼讀：

- 舊 `desc`（純文字，可能多行）→ 依換行切成多個 `check:null` 的行，行 ID 用「卡片 ID＋行序」決定性產生，所以遷移重跑不會產生不同的 ID。空白行保留成空字串的行。原文另存 `legacyDesc`。
- 舊 `times[]` → `events` 集合，ID 不變，掛在卡片的 `timeIds`（不自動猜它屬於哪一行）。
- 權益部有 20 筆多行說明，遷移驗證要逐筆比對「各行文字用換行接回去＝原文」。

### 5.4 版本與舊的「完成這一段」

- `cardVersions` 文件只能新增、不能改、不能刪；規則要求版本號必須等於同一批寫入後卡片的 `version`。
- 舊的分段紀錄（`fromEv` 有值的 12 筆）是獨立的完成紀錄，被週報「本週完成」、工作報告、燈號（`roundAt`）用到。遷移時原樣搬成 `state:done` 的卡片並保留 `fromEv`、`round`，**不轉成版本、不刪**。04 再決定畫面上怎麼呈現（8-9）。

### 5.5 權限規則方向

- 預設全部拒絕，逐條開放。
- 判斷角色的方式：規則裡讀 `roles/{uid}`。不使用 custom claims（那需要 Cloud Functions 或服務帳戶）。
- `roles` 只有 `super` 能寫；唯一例外是「邀請核銷」：同一批寫入裡，邀請文件從未使用變成 `usedBy＝自己的 UID`、還沒到期、沒被撤銷，同時只新增邀請上寫明的那個部門角色。兩個人同時核銷時交易只會成功一個。
- 部門資料的寫入：`roles/{uid}.depts[文件的 deptId]` 存在才允許，而且不能改文件的 `deptId`。
- 秘書處會議編輯：`grants/meetingEdit` 還沒到期、對象是 `report＝true` 的卡片、操作者是秘書處角色，三者都成立才允許跨部門修改。這把現在只擋得住介面的授權變成真的。
- 全會活動／全會會議：`events` 的範圍欄位只有活動部角色能設成全會活動、秘書處角色能設成全會會議。
- 預約互斥：核准時在交易裡新增 `bookingSlots/{時段ID}`，規則要求該文件不存在；兩筆同時核准只會成功一筆。時段 ID 由固定格線（例如 30 分鐘）決定。
- 稽核紀錄：只能新增，`uid` 必須等於登入者、時間必須等於伺服器時間。
- 每條規則都要有模擬器測試：未登入、一般帳號、別部門的管理員、被撤權的人，各自嘗試寫入都要被拒絕。

第一位總管理員怎麼來：由你在 Firebase 主控台手動建立一份 `roles/{你的UID}`（一次性步驟，會寫成操作清單）。不在規則裡寫死信箱。

## 6. 資料備份、遷移與回復策略

### 6.1 原則

- 分支與遷移程式**永遠不寫** `data.json`、`data-*.json`、`archive/`。遷移只讀它們。
- 所有演練在模擬器或開發專案進行；正式遷移要你逐次確認。
- 不做雙向同步（兩邊同時可寫最容易出資料事故）。採「凍結 → 搬 → 驗 → 切換」，一次一個部門。

### 6.2 備份

- 來源備份：JSON 檔本身就在 Git 裡，每次存檔一筆 commit。遷移前記下來源 commit 的 SHA 與每個檔案的 SHA-256，寫進遷移報告與 `legacy/{部門}`。建議你在遷移當下打一個 Git 標籤（例 `pre-firestore-日期`）。
- 新資料庫的備份：免費方案沒有排程備份。做一個只有總管理員能用的「匯出全部資料（JSON）」，格式與現在的匯出備份相容。備份檔要放哪裡、多久一次，見 8-11。

### 6.3 遷移流程（01B 寫成可重跑的程式）

1. 讀指定 commit 的 10 個 JSON 檔，先用現有的 `migrate`／`normalize` 規則升到 schemaVersion 13（確保舊版本也吃得下）。
2. 依 5.1 的對照轉成文件。**所有文件 ID 由舊 ID 決定性產生**（卡片、議題、週報、標籤、時間標記沿用舊 ID；行 ID＝卡片 ID＋行序），所以重跑是覆寫同一份，不會重複。
3. 跨資料連結照搬並驗證：`events[].issueId` → 議題存在；`issues[].markers[].evId／tmId` → 卡片與時間存在；`follows[].ref`；`fromEv`。斷掉的連結不丟棄，列進報告。
4. **不搬**：`sync`（含三種加密權杖）、`pwKdf`、`pwHash`、`members[].kdf`、`members[].tok`。只把 `members[].id` 與 `name` 存進 `legacy/{部門}` 當對照。
5. 產生報告：每個集合的來源筆數與寫入筆數、每筆說明的行數與原文比對、連結檢查結果、略過與失敗的項目與原因。
6. 重跑一次，確認文件數與內容雜湊完全相同。

執行方式：在模擬器用測試身分直接寫。正式遷移建議做成「總管理員登入後在瀏覽器執行的匯入頁」（走同一套規則，只有 `super` 能匯入），這樣不需要產生任何服務帳戶金鑰。01A 再確認這個做法與規則不衝突。

### 6.4 時間與時區

舊資料的日期時間是沒有時區的字串（例 `2026-11-04T14:00`、`2026-11-10 21:54`），實際上是台灣時間。遷移時一律當作 `Asia/Taipei` 轉成時間戳，另外保留原字串與「是否只有日期」的旗標，全天與跨日事件才不會差一天。

### 6.5 切換策略

- 在 `dept/config.js` 給每個部門一個資料來源開關（`github`｜`firestore`），資料層做成轉接：上層的 `state` 形狀與 `render()` 不變，底下換實作。
- 順序：水果部（測試部門）→ 一個自願的小部門 → 其餘部門 → 最後權益部（資料最多）。
- 每個部門切換當下：公告暫停編輯幾分鐘 → 跑遷移 → 看報告 → 打開開關（要合併一個只改開關的 PR）→ 該部門的人用 Google 登入確認。
- 舊 JSON 檔留在 repo 當唯讀備份，不刪。

### 6.6 回復

| 時間點 | 回復方式 | 會不會掉資料 |
|---|---|---|
| 切換前任何時候 | 不合併，或 revert 該 PR | 不會，正式資料沒被碰過 |
| 某部門切換後、03 上線前 | 把開關改回 `github`；切換後的新修改用「匯出成 schemaVersion 13 的 JSON」倒回去，由你用看板的匯入備份寫回 | 不會（結構還能一對一對回去） |
| 03 上線後 | 仍可匯出成 JSON，但逐行的核取狀態會被攤平成文字（例如行首加記號） | 會失去核取方塊與行層級的時間關聯，文字不會掉 |
| 全部部門切換並穩定運作後 | 作廢 GitHub 權杖，舊的寫入路徑正式退場 | 這一步之後不能回到 GitHub 寫入模式 |

權杖作廢是不可逆的那一步，要你親自做，而且放在最後。

### 6.7 遷移後的隱私收尾

- 作廢權杖後，公開檔案與 Git 歷史裡那些加密權杖就沒有用處了。
- 密碼雜湊還在 Git 歷史裡，改寫歷史不實際（每個人的複本都還在）。做法是通知 11 位現有身分：如果看板密碼跟別的服務相同，請去改別的服務的密碼。
- 舊 JSON 檔要不要在切換後改成不含 `sync`、`members` 密碼欄位的版本，由你決定（8-13）；那會是一次你親自確認的資料檔修改。

## 7. 各階段執行順序與驗收條件

### 7.1 分支與預覽方式的問題

現在的流程是「合併到 main 就上線」。這次改版的中間狀態（例如只有後端、沒有登入畫面）不能直接上線。建議：

- 每個階段一個分支、一個 PR，照舊由你合併。
- 還沒完成的新資料層用部門開關藏住：main 上有程式，但只有水果部（`?d=fruit`）走新路徑，其他部門完全不受影響。
- 需要給你看畫面的階段（03 之後）附本機截圖；要不要另外準備一個預覽網址，見 8-12。

### 9.3 規格本身要請你確認的地方

- 規格沒有指定正式切換發生在哪一階段。本計畫放在 02 之後（7.2 第 5 步）。
- 02 要求「會長室總管理員統一審核」，同時現有功能有「部門管理員可以新增身分」。本計畫的理解：部門管理員不能自己加人，只能請會長室產生 QR 或審核申請。如果你希望部門管理員能邀請自己部門的編輯者，規則要多一條。
- 規格的角色只有「唯讀／部門管理員／會長室總管理員」。秘書處的會議編輯、點名，活動部的全會活動，是「部門角色＋部門別」決定，不另設角色。
